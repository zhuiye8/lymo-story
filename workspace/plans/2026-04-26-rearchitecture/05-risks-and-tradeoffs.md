# 05 · 风险、权衡与逃生通道

## 5.1 三类风险盘点

### A. 技术风险

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|------|------|------|---------|
| A1 | Graphiti+Kuzu 集成失败（API 不兼容 / 数据迁移失败） | 中 | 高 | 在分支上做 PoC，留 1 周缓冲；保留旧 KG 作为 fallback |
| A2 | autonovel slop_score 中文化召回率低 | 中 | 中 | 用 100 条人工标注样本验证，召回率 < 80% 不上线 |
| A3 | Per-Role agent 让 LLM 调用数翻倍 | 高 | 中 | 限制 ≤ 5 个 in-scene roles 并行；只对主要角色启用 |
| A4 | WebNovelBench 8 维度评分对中文短章节失真 | 低 | 中 | 评测前在 5 章上手工对照，发现失真就调整维度权重 |
| A5 | 新架构与现有 LangGraph 节点冲突（state 字段过多） | 中 | 中 | 严格 schema 演进规则：只加不删，废弃字段保留 2 个 Phase |

### B. 产品/质量风险

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|------|------|------|---------|
| B1 | Phase 0 后基线分数太高，后续 Phase 无空间提升 | 低 | 高 | 评测维度多元，单 Phase 不需在所有维度都提升 |
| B2 | Phase 1 + autonovel 资产中文翻译走样 | 中 | 高 | 翻译后人工 review，并在小说生成上 A/B 对照 |
| B3 | 写得"太像 autonovel 风格"失去本土网文味 | 中 | 高 | autonovel 资产作为**底线规则**，不是**正向风格**；voice.md 单独定 |
| B4 | 每章成本上涨 3-5 倍（多个 critic + 多候选） | 高 | 中 | 每个 Phase 末给 PM 报告成本；用便宜模型做 critic |

### C. 进度/沟通风险

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|------|------|------|---------|
| C1 | Phase 之间发现"前一个 Phase 设计有缺陷" | 高 | 中 | 接受 1 周的 buffer；前 Phase 出口标准放宽容忍度 |
| C2 | PM 反馈延迟，工程师无法继续 | 中 | 高 | 工程师明确"如不回复 X 天则按推荐选项执行"的默认决策 |
| C3 | Phase 5 决定要不要做的时机太晚 | 低 | 低 | Phase 4 末重新审视，必要时调整顺序 |
| C4 | 用户中途增加新需求打乱计划 | 高 | 中 | 新需求统一进 `workspace/inbox/from-pm/`，PM 评估优先级 |

## 5.2 关键权衡

### 权衡 1：质量 vs 成本

**事实**：
- Phase 0 基线评测增加 ~¥0.05/章
- Phase 1 增加 1-2 个 LLM 调用 → +¥0.05-0.1/章
- Phase 3 Per-Role × 5 角色 → +¥0.1-0.3/章
- Phase 6 多候选 × 3 + Pairwise → +¥0.3-0.5/章
- **6 个 Phase 全做完**，单章成本从当前 ¥0.09 涨到 ~¥0.7-1.2

**应对**：
- 把 critic agent 全部用 DeepSeek-V4-Flash（¥0.0023/调用）
- 写作主力按 PM 决策 5 选择
- 单章上限 ≤ ¥1（超出则 Phase 出口标准里报警）

### 权衡 2：架构纯净 vs 工程实用

**事实**：
- 蓝图设计了 11 个核心内核，理想架构非常优雅
- 但工程上要分 6 Phase 实施，中间状态会"半新半旧"
- 例如 Phase 1 做完时，Camera 还是老的，Per-Role 还没引入

**应对**：
- 接受**中间状态丑**，只要每个 Phase 末是可工作的
- 不强求"架构完美"，每个 Phase 末跑通基线测试即可

### 权衡 3：自研 vs 引入

**事实**：
- 调研发现 3 个成熟项目（Graphiti / autonovel / WebNovelBench）都建议直接引入
- 但每引入一个外部依赖，就增加一份运维成本
- Graphiti 还在更新（2026-04），不是僵死项目，但仍可能 break

**应对**：
- 只引入"我们做不到的能力"（Graphiti 自动 provenance）
- 不引入"我们能做但慢"的（如 autonovel 整套 pipeline）
- 每个引入项有 fallback 方案

## 5.3 失败逃生通道

### 触发条件 → 应对

| 触发条件 | 应对动作 |
|---------|---------|
| Phase 0 完成后基线评分较真实人写小说差距太大（< 3.0/10） | 不做后续 Phase，先调 prompt 基线 |
| Phase 1 完成后基线评分提升 < 5%（远低于 15% 目标） | 暂停 Phase 2，重新审视 autonovel 资产是否中文化失真 |
| Phase 2 Graphiti 集成失败 | 回退到强化手写 KG 方案（决策 2 选项 B），多花 1-2 周 |
| Phase 3 RoleCognition 让生成质量反降 | 回退到无 Per-Role，但保留强化 SceneCard |
| 任何 Phase 后单章成本超过 ¥1.5 | 暂停，重新评估模型分层 |
| 用户中途反馈"还是难看" | 抽 1-2 章人工分析，找出最大问题，跳到对应 Phase |

### 全局回滚

每个 Phase 开始前都做：
1. `data/story.db` 备份（已有机制，文件名 `story.db.bak_<phase>_<ts>`）
2. Git tag：`pre-phase-{n}`
3. 关键 schema 变更前先在新分支跑 1 周再合并

## 5.4 关键不确定性

下面这些**调研不能完全消除**，必须在执行中验证：

1. **WebNovelBench 8 维度评分对短章节是否准确**？论文用的是完整小说，我们用单章评测可能失真。Phase 0 必须做手工对照。

2. **autonovel slop_score 中文化后召回率**？英文 banned words 直译为中文不一定准。需要建中文坏样本库验证。

3. **Per-Role agent 是否真能减少角色雷同**？CreAgentive 论文证明在英文场景有效，中文未验证。Phase 3 完成后必须在 D5 维度看显著提升才算成功。

4. **Graphiti 在中文实体抽取上的准确率**？官方主要测试英文。Phase 2 必须做中文实体抽取的准确率评测。

5. **DeepSeek V4 系列在长篇上的稳定性**？论文 SOTA 是 Qwen3-235B，V4 还没人测过。决策 5 的 A/B 对比是关键。

## 5.5 给 PM 的最后提示

如果只能问工程师 3 个问题，建议问：

1. **"Phase 0 真的能 1.5 周做完吗？是否低估了？"**
   - 工程师答：1.5 周指的是核心评测器 + 跑现有数据 + 前端展示。如果加上中文坏样本库精修，可能要 2 周。

2. **"为什么不一次性引入所有论文的方法（CreAgentive + DOME + Graphiti）？"**
   - 工程师答：要分 Phase 是因为每个改动都需要在基线上验证。同时引入会让"哪个改动起作用"无法判断。

3. **"如果 PM 决策推迟 2 周怎么办？"**
   - 工程师答：建议 PM 先单独决策 1（渐进 vs 重写）和 6（Phase 顺序），其他可以在 Phase 0 期间补决策。Phase 0 的 1.5 周给了缓冲。
